.NET : WINE MONO OU MICROSOFT

Wine Mono est une alternative à .NET Framework jusqu’à 4.8.1. Il ne remplace pas .NET 6, 8 et les runtimes modernes. Il peut suffire à certains launchers, configurateurs et jeux ; d’autres demandent le framework Microsoft.

BATOCERA FOURNIT DÉJÀ MONO

Batocera v41 fournit un runtime partagé avec Wine TKG (sources : Mono 9.3.0). Batocera v43.1 fournit un runtime partagé sous /usr/share/wine (sources : Mono 10.4.0). Les versions modifiées et les runners personnalisés peuvent différer. La présence d’un dossier partagé ne prouve pas que le préfixe l’utilise. Wine peut aussi enregistrer Mono dans le préfixe.

Le diagnostic distingue Mono, indices de .NET Microsoft, état mixte, traces non identifiées et absence de composants identifiés. Une clé NDP ou un numéro Release ne suffit pas à identifier Microsoft : Mono peut créer ces mêmes clés. La détection n’est pas un test d’exécution.

DANS LE WORKFLOW

Après l’essai du jeu, ouvrir .NET dans le menu de résultat (création ou mise à jour). En création, cette option est aussi accessible dans les composants Winetricks.

Installer / mettre à jour Mono télécharge le MSI stable officiel avec vérification SHA-256 et l’installe dans une copie locale du préfixe de travail. Le paquet x86 couvre aussi x86-64. Cela ne met pas à jour le Mono partagé de Batocera.

Remplacer Mono par .NET Framework 4.8 utilise Winetricks remove_mono puis dotnet48 avec le runner choisi. Les états mixtes ou incertains sont refusés plutôt que forcés. Si Microsoft est déjà identifié, la Toolbox ne le réinstalle pas automatiquement. L’installation peut échouer selon le runner et l’architecture du préfixe ; consulter le journal.

Avec Proton/UMU, le runner peut réappliquer sa propre version Mono. Préférer sa version fournie sauf besoin confirmé, puis tester un deuxième lancement. La dernière version Mono n’est pas forcément adaptée à un ancien runner.

COPIES DE SÉCURITÉ

Avant installation, une copie du préfixe est conservée dans backups/dotnet sous le dossier de la Toolbox. Le dossier principal du jeu identifié via autorun est exclu ; les liens sont copiés sans suivre les cibles, notamment les sauvegardes externes. L’archive source reste intacte. Ne supprimez pas le dossier du jeu pour restaurer cette copie : elle ne le contient pas. Le journal indique le chemin exact de la copie. En cas d’échec, aucune restauration automatique n’est effectuée.

La fonction reste expérimentale tant que l’installation, la relance et la conservation dans l’archive n’ont pas été validées sur Batocera.

INSTALLATION LOCALE ET RESTAURATION

Les installateurs travaillent dans une copie sous state/dotnet-work, hors du dossier des ROMs. Le dossier du jeu n’est pas copié. Le système de fichiers local doit permettre l’échange atomique fichier/dossier utilisé par certains Wine TKG ; cette capacité est testée avant installation. UWT_DOTNET_WORK_ROOT permet de choisir un autre emplacement local si nécessaire.

Les métadonnées .REPARSE_POINT de TKG sont préservées sans être parcourues ni déréférencées. Leurs ancres ${WINEPREFIX} sont adaptées à la copie puis au préfixe final. Le runtime partagé et les DLL des runners restent intacts.

Le résultat n’est transféré au préfixe de travail qu’après réussite et vérification. Une erreur d’installation laisse le préfixe initial en place et conserve la copie locale pour analyser ses journaux. Le MSI Mono écrit aussi windows/temp/uwt-mono-install.log dans cette copie. Une erreur pendant le transfert déclenche le retour des entrées déjà remplacées ; si ce retour échoue, le journal indique les fichiers de récupération conservés. Prévoir l’espace pour la sauvegarde, la copie locale et le transfert.

Le bouton Restaurer une copie de sécurité permet de repartir d’un état antérieur. Les copies sont classées de la plus ancienne à la plus récente : après plusieurs installations incomplètes, choisir une copie antérieure au premier essai. Le dossier du jeu et les cibles de sauvegardes externes restent en place ; les autres fichiers du préfixe reviennent à la date choisie. L’état courant est copié avant restauration.

RUNNERS UMU

Pour remplacer Mono par Microsoft .NET, une copie temporaire de Winetricks désinstalle chaque GUID Mono séparément et nettoie les clés NDP v3.5/v4 des vues 32 et 64 bits lorsque Mono est détecté. Cela traite les entrées Mono multiples et les traces de compatibilité de GE-Proton qui peuvent faire croire à l’installateur que .NET est déjà présent. Le Winetricks de Batocera n’est pas modifié. Une version de script non reconnue est refusée.

Les opérations .NET utilisent directement le moteur Wine fourni par le runner sélectionné, y compris pour les installateurs EXE. Elles ne lancent pas ces installateurs comme des jeux UMU/Proton : regedit, winecfg, les EXE et wineserver doivent rester sur le même moteur et le même préfixe local. Le lancement habituel du jeu reste géré par UMU. La réussite exige aussi le marqueur Winetricks dotnet48 : la seule présence de .NET 4.0 ne suffit pas.

FENÊTRES PENDANT LES TESTS

Les essais .NET sont interactifs : aucun -q Winetricks ni /qn MSI. Les fenêtres Wine Mono / Microsoft apparaissent et le terminal affiche le journal en direct. Valider les écrans de l’installateur, sans demander de redémarrage immédiat de Wine. Winetricks utilise zenity/kdialog pour ses questions si disponible, sinon le terminal reste accessible. Alt+Tab permet de retrouver une fenêtre derrière la toolbox. Le plein écran du terminal est temporairement retiré puis restauré si wmctrl et xprop sont disponibles ; les préférences ne sont pas modifiées.

La limite souple de fichiers ouverts est relevée à 65536 pour le processus d’installation et ses enfants, seulement si elle est inférieure et si la limite dure le permet. La limite dure et les réglages système restent inchangés. Les valeurs précédentes et effectives sont journalisées. Cela traite une limite héritée trop basse ; cela ne garantit pas la compatibilité de .NET avec le runner.
